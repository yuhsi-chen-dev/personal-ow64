## 已驗證到哪

寫入路徑在真實資料庫上走過（查資料庫確認，不是看畫面）：結構、讀取、寫入、

畫面在 Chrome 上實際操作過（2026-08-23）：

- **手機尺寸的破版修掉了**。原因是聚焦格子底部那條打卡按鈕沒有 `whitespace-nowrap`，
  格子窄到約 60 px 時「本週已完成」斷成兩行，整條變兩倍高往上蓋掉標題。
  現在條是固定 `h-7`、字不換行、格子上用短標籤（期間字樣讓給面板），
  而且格子的內容區在條的上緣就收邊——否則沒有底色的「記一次」後面會透出第二行字。
- 順手修掉一個資料 bug：面板原本把點下去當時的 `Cell` 物件存進 state，存檔之後
  拿到的還是舊快照，輸入框留著舊字，再按一次儲存就把剛改好的名字覆蓋回去。
  現在只記「選了哪一格」，每次 render 從新的 board 撈。
- 桌機淺色／深色都看過；建立計劃表 → 改核心目標名稱 → 建次目標 → 移除次目標 →
  刪整份計劃表，整條走完。

今天頁的狀態判準（`lib/today.ts`）有四種：`due` 今天要做、`done` 今天做了、
`idle` 今天沒它的事（每週型本週稍早做過、里程碑早就完成、累計已達標）、
`mantra` 信念型只看不打卡。**今天做完的要留在今天的清單裡**，不能掉成 idle——
否則做完一件事會讓分母跟著少一，計數從 3/9 變 3/8，看起來像什麼都沒發生。
這條有測試釘住。

線上（production）走過一整輪（2026-08-24）：建立 → AI 拆 8 個次目標 → 採用 →
AI 拆 8 項行為 → 採用 → 打卡 → 改名 → 移除一格 → 刪計劃表。全程 console 沒有錯誤。

- **四類追蹤方式都在真實 production 資料庫上操作過了**（AI 產的那 8 項剛好四型齊全）：
  `habit` 記一次、`cumulative` +1、`milestone` 完成、`mantra` 只看不打卡沒有按鈕。
- **封存在線上成立**：移除一個打過卡的次目標後，回顧頁仍顯示「3 筆紀錄，含已收起的格子」。
  同一塊接著重填 8 項新行為，沒有撿回舊紀錄。
- **AI 沒有撞到 Vercel 的執行時間上限**：次目標約 4–6 秒，行為兩次都在 9 秒內。
  所以**不加 `maxDuration`**——沒撞到就不要為不存在的問題先寫設定。
- **資料隔離（讀取端）在線上成立**：另一個 Google 帳號帶著 A 的 plan id 開網址拿到 404
  （`loadPlan(userId, id)` 查不到就 `notFound()`）。
- 手機實機由使用者走過今天頁與打卡，回報沒問題。
- 深色／淺色、刪除前列出「連同 N 個次目標、N 項行為、N 筆紀錄」的數字都正確（含已封存的）。

兩個線上才看得到的觀察，都不影響正確性：

- **今天頁「第一次」打卡後，上方計數會慢幾秒才動**。按鈕立刻變「今天已完成」，
  但 `0/6` 停了約 4 秒才變 `1/6`；同一次工作階段的第二次打卡就即時跳。
  最可能是 Neon 閒置 suspend 後的冷啟。手機上「今天第一次打卡」會看起來像沒反應。
- AI 那個 server action 的 POST 在 DevTools 記到的狀態碼是 503，但結果正常回來、
  畫面也正確，兩次都一樣。使用者看不到異常；下次線上出怪事時值得先想到它。

（已完成）**手機版面的 UI。** 主要功能與部署都完成了，下一塊就是這個。

上線之後在真機上用才發現：**桌機看起來很順的版面，在手機上很不順**——
要一直移動畫面才點得到某些按鈕。而手機不是次要情境，是主要情境：
不會無時無刻開著電腦，平常查看與打卡本來就是拿手機。今天頁的存在理由更是如此。

這件事對得上 `CLAUDE.md` 的優先序第 3 條（填寫與打卡的順手程度），
也對得上第 2 條——**手機上看不清楚的視覺化等於沒有視覺化**。

要注意的是：先前那次「手機尺寸的破版修掉了」是**把 Chrome 的容器寬度壓窄**驗的，
不是真機。真機才暴露出「點得到／點不到」這一層，視窗寬度模擬不出手指與捲動。
所以這次每一項改動都要在真機上確認，不要再用壓寬度當作驗過。

還沒盤點是哪些畫面、哪些按鈕最痛。動手前先在手機上把四個路由各走一遍，
把「要移動才點得到」的地方一個一個記下來，再決定改的順序——
不要一次重寫版面，那會把已經驗過的東西一起弄壞。
