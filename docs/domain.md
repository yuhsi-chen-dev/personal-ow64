# 領域模型

實作前務必照這個結構，弄錯就整份重來。程式碼的唯一實作在 `lib/mandala.ts`。

## 9×9 的組成

一份計劃表 = 9×9 = 81 格，由 9 個 3×3 區塊組成：

- **中央區塊的中心格**：核心目標，整份表唯一 1 個，座標 `(4,4)`。
- **中央區塊其餘 8 格**：次目標，共 8 個。
- 每個次目標**同時也是**外圍某一個 3×3 區塊的中心格。同一份資料出現在兩處，
  儲存時只存一份，渲染時映射到兩個座標，**不要存兩筆**。
- 每個外圍區塊的其餘 8 格：該次目標底下的**具體行為**，8 × 8 = **64**。
  這 64 格就是產品名稱裡的 64，也是唯一可被追蹤／打卡的單位。

合計：1 + 8 + 8（鏡像）+ 64 = 81。

核心目標與次目標**不直接被追蹤**，它們的進度一律由底下的具體行為彙總而來。

## 座標慣例

`(row, col)`，0-indexed，0..8。中央區塊是 rows 3..5 / cols 3..5。

每個 3×3 區塊裡 8 個非中心格有固定的 row-major 順序（slot 0..7），
次目標的編號與行為的編號都用這個順序。中央區塊的次目標位置、外圍區塊的中心格、
以及行為的位置，全部由 `lib/mandala.ts` 的同一組位移表產生——
**不要在渲染、匯出或任何其他地方重寫一次映射邏輯**。

`lib/domain.test.ts` 會驗證 81 格恰好被指派一次、組成比例正確、
每個次目標剛好一個本體加一個鏡像。改動座標邏輯後這個測試必須仍然過。

## 未填滿是常態

使用者不會一次想出 64 項。所有渲染、統計、匯出都必須容忍空格，
不要用「填滿才算有效」的前提寫邏輯。資料層的表現方式是「沒填的 slot 就是沒有那一列」。
彙總時空的次目標回傳 `null` 而不是 `0`，由呼叫端決定怎麼顯示。

已封存的次目標與行為（`archived_at` 不是 null）對盤面來說**就是沒填**，
讀取時一律濾掉。位置也跟著空出來，可以重填成別的東西——見
`decisions/0009-soft-delete.md`。

## 今天的分母只認週期

今天頁的計數（`lib/today.ts` 的 `tally`）分母只算習慣型。里程碑與累計沒有 `cadence`，
就沒有「本期應做量」，也就沒有今天的應做量——它們的狀態是 `open`：看得到、按得下去、
不計分。混進分母的話，一個一年期的目標會讓今天的分數永遠差一。理由見 `decisions/0016`。

## 進度公式只能有一份

所有百分比計算走 `lib/progress.ts`，圖表元件不可以自己寫一份。
次目標的 8 格進度、核心目標的總進度，都是由這裡往上彙總。

跨型態彙總時一律先各自正規化成 0..1 再平均。習慣型的分母是
「統計區間內應達成的期數 × 一期要做幾次（`timesPerPeriod`，未設定等同 1）」，
**不是天數、也不是「有紀錄的天數」**——前者會讓每週一次的行為永遠低分，
後者會讓久沒做的行為看起來很完美。

分子是**每期實際次數但不超過該期的需求**：某週跑了 5 次不能補上另一週的空白。
少了這個上限，一次補做就能把整段區間灌成滿分，見 `decisions/0015`。

**信念型（`mantra`）沒有進度，彙總時要濾掉而不是算成 0。**
一格信念會讓整個次目標永遠上不了 100%，這是最容易寫錯的一條。

實作在 `lib/progress.ts`，四種 `trackingType` 的定義見 `decisions/0008-tracking-taxonomy.md`
（習慣型的一期次數見 `decisions/0015-habit-times-per-period.md`），
資料表結構見 `decisions/0004-single-log-table.md`。
