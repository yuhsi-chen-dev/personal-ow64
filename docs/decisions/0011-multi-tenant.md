# 0011. 從單人工具改成多租戶（但不是協作工具）

- 狀態：已採納
- 日期：2026-08-23

## 決策

上線之後會有其他人使用。每個使用者有自己的帳號、自己的計劃表，**彼此完全看不到對方**。

登入用 Auth.js（NextAuth v5）+ 一個 OAuth provider，session 走 JWT，不另建使用者資料表。
`plans` 加一欄 `userId`，其餘三張表靠 FK 往上追到 `plans` 決定主人是誰。

這一段回答的是 [0005](0005-deploy-vercel-neon.md) 刻意留著沒答的問題：「等到要做手機打卡、
跨裝置同步時才需要帳號，屆時再比 Neon Auth 與 Auth.js」。選 Auth.js 而不是 Neon Auth，
理由跟 0005 當初不開 Neon Auth 一樣——它會把自己的一組 schema 放進資料庫，
跟 `db/schema.ts` 對不起來；JWT session 則連使用者資料表都不用建。
0005 本身沒有被推翻，Vercel + Neon 的選型照舊。

## 什麼變了、什麼沒變

**變了**：`CLAUDE.md` 原本寫「單一使用者為自己做長期目標管理」「單機單使用者，
目前沒有帳號系統，也不假設有網路」。這三句從今天起是假的，已一併改掉。

**沒變**：**不是協作工具。** 沒有分享、指派、留言、團隊、公開計劃表。
多租戶只是「很多個各自獨立的單人使用者」，不是「使用者之間有關係」。
這條界線很重要——一旦有分享，就需要權限模型（誰能看、誰能改、能不能轉讓），
那是完全不同量級的東西。**要加分享功能請開新的決策編號，不要當成這一篇的延伸。**

判斷取捨的優先序也沒變，`CLAUDE.md` 那四條照舊。

## 為什麼擁有權必須落在寫入層，不能只在查詢層

這是這篇最重要的一條。

改之前，`listPlans()` 回傳所有計劃表、`loadPlan(planId)` 拿到 id 就給。
八支 server action 裡，除了 `createPlan`（在建新的，沒有既有 id 可言），
其餘七支引用的 id 全部直接來自表單欄位，沒有一支問過主人是誰。
**只在讀取端加 `where userId = ...` 是不夠的**——攻擊者不需要看得到別人的表，直接 POST 別人的 `planId` 就能改、能刪。
`removeActionCell` 收的甚至只是一個 `actionId`，得往上 join 兩層才知道主人是誰。

所以：

1. `db/writes.ts` 的**每一支**寫入函式都必須吃 `userId`，而且 WHERE 條件要涵蓋它。
   不是「呼叫端記得檢查」，是「不帶使用者就寫不進去」——讓它在型別上就是必填。
2. 行為與紀錄沒有自己的 `userId`，要 join 回 `plans`。這是刻意不反正規化的：
   多存一份 userId 就多一個會不同步的地方，而且一格資料的主人本來就該由它的
   計劃表決定。
3. 每一支都要有整合測試，測的是「B 拿 A 的 id 打進來會被擋下」，
   不是「A 自己操作正常」。後者過了不代表前者。

## 後果

- `plans` 加 `userId`，需要新的 migration。既有資料要指定主人或清掉。
- `db/queries.ts` 與 `db/writes.ts` 的簽名全數改變，`app/actions.ts` 從 session 取得
  使用者身分往下傳。沒有登入時 server action 直接拒絕，不要靜默當成沒事。
- 免費額度變成所有使用者共用：Vercel Hobby 限非商業用途，Neon 的儲存與運算是一份。
  這兩件事在使用者變多時會先撞到，不是效能問題而是條款與額度問題。
- **別人的資料進了這個資料庫。** 目前沒有隱私政策、沒有資料匯出、沒有刪除帳號。
  給幾個認識的人用還可以，真的開放註冊之前至少要有「刪帳號連同資料一起刪」的路徑。
  這是未做事項，不是已解決事項。
- 之後的 AI 生成會把使用者輸入的目標送到外部 API，要讓使用者知道。
  見 `decisions/0012`（尚未撰寫）。
- `docs/deploy.md` 要多一組環境變數（OAuth 的 client id／secret 與 session secret）。
