# 0009. 移除一格＝封存，不是刪掉紀錄

- 狀態：已採納
- 日期：2026-08-23

## 決策

從盤面上拿掉一個次目標或一項具體行為時，走哪一條路由「這一格底下有沒有紀錄」決定：

| 情況 | 做法 | 為什麼 |
|---|---|---|
| 沒有任何打卡紀錄 | 直接 `DELETE` | 沒有歷史可失，留一列封存的空殼只是垃圾 |
| 有打卡紀錄 | 填上 `archived_at`，紀錄原封不動 | 歷史不能因為使用者改主意就消失 |

判斷寫在 `db/writes.ts` 的 `removeAction` / `removeSubGoal`，回傳 `"deleted"` 或
`"archived"`。次目標被封存時，底下的行為要**一起**封存。

**整份計劃表的刪除不走這條路**：`deletePlan` 是真的刪，靠 FK cascade 帶走次目標、
行為與紀錄。整份表是使用者自己建的容器，他說不要就是不要；一格則是那個容器裡的內容。

## 為什麼不是硬刪

CLAUDE.md 的第一優先序是「追蹤資料的正確與完整（歷史紀錄不能遺失或被覆蓋）」。
`logs` 對 `actions` 是 `on delete cascade`，硬刪一格會連同那格所有的打卡一起消失——
使用者只是想把填錯的格子換掉，卻連著把三個月的紀錄一起丟了，而且**沒有任何提示**。

## 為什麼唯一索引要改成條件式

原本 `(plan_id, position)` 與 `(sub_goal_id, position)` 是無條件唯一。封存的列如果還佔著
位置，重填同一格就會 upsert 到那一列上——**連同它的舊紀錄一起復活**。使用者以為自己
開了一項新行為，進度卻莫名其妙從 40% 起跳。

所以兩個索引都加上 `where archived_at is null`：封存過的列不佔位置，重填同一格會拿到
全新的 id 與全新的紀錄。對應地，`upsertSubGoal` / `upsertAction` 的 `onConflictDoUpdate`
必須帶 `targetWhere: isNull(archivedAt)`，條件不一樣就對不上索引，插入直接爆。

migration 在 `db/migrations/0002_soft_delete.sql`。

## 後果

- `loadPlan` 一律濾掉已封存的次目標與行為。盤面上它們就是不存在。
- 回顧頁的年度熱圖改走 `loadPlanLogs`，那支查詢**不濾封存**——收起一格不該讓
  那段日子從歷史上消失。底下的月趨勢仍然只算還在盤面上的行為，因為它問的是
  「現在這張表做得怎樣」。
- `findAction` 也要濾掉封存的，否則已收起的行為還能被打卡。
- 目前沒有「復原」的入口。封存的資料還在資料庫裡，要救得手動下 SQL。
  真的常常誤刪再做 UI，不要先蓋。
- 以上都在 `db/write-path.test.ts` 對真實資料庫釘住了：硬刪與封存各一個案例、
  紀錄不能少、封存過的位置可以重填而且不撿回舊紀錄。
